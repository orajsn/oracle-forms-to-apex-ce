# Generated prototype output

The opt-in prototype route turns an approved, redacted source version into a
bounded native APEX prototype. Unsupported behavior and missing dependencies
remain visible remediation work. It does not promise behavioral equivalence.

## Business-user path

1. Open the project and select its prepared source version.
2. Review prototype scope and the code units approved for external AI processing.
3. Confirm redaction, processing permission and synthetic-prototype scope.
4. Submit once, then inspect the existing run. Do not resubmit an uncertain run.
5. When the run says **Generated prototype**, choose **View prototype output**.
6. Download the generated prototype package when the retained evidence is valid.

The output check is read-only. Download rechecks the exact package against its
source, validation, import, runtime and export evidence. A changed source/owner/
target or missing proof blocks the download; no conversion is replayed by a GET.

The package contains its actual conventional APEX SQL export, exported APEXlang,
mapping, omissions and technical evidence. Use the versions and requirements
recorded in that package. Do not infer compatibility with an unspecified target.
Generated is not business accepted. This route does not claim an independent
clean-schema reimport of the exported package or unlock the strict accepted-output
download route.

## Operator wiring

All new capabilities default to disabled. Use the guarded upgrade preparation
options for the exact HTTPS FOX origin, protected focused-profile path/hash and
measured runtime-worker hash. The profile is a metadata-only envelope, separate
from the existing converter execution-target profile and credential file. The
existing protected read-only profile mount is reused; no new public port, OCI
resource, IAM policy or network rule is required by these adapters.

Configure `qa.operator.prototype_host` on the existing supported rootless Linux
operator host. Its protected configuration names exact container/image identities,
the measured target profile, private state directories, existing converter bearer
credential and dedicated original-workspace runtime account. The credential is
not placed in source, the application package, command arguments or the UI.
Only application login is needed; workspace administrator privileges are not.

The host worker discovers unclaimed requests, checks current authority, executes
the bounded browser check, and returns hash-bound evidence to the original job.
One worker owns a request. Expired requests and claimed/uncertain attempts remain
preserved; do not delete their files to force a retry. Discovery is bounded to100
candidates. An operator must investigate excessive expired backlog separately.

Run the installed host/module/UID, protected-profile access, target/account and
actual browser checks before advertising readiness. A healthy worker or passing
synthetic test does not prove conversion. Bind the host configuration to the new
converter identity after a paired upgrade. Stop/quiesce the worker before a
backup, restore or subsequent deployment, and observe existing outcomes before
resuming. Do not assume the standalone worker is covered by older service units.

On rootless cgroups v1, Podman may ignore CPU/memory/pids flags. That known warning
is not treated as a runtime-test failure, but resource isolation is not claimed.
The explicit conmon lifetime and request expiry still bound browser execution.
No host cgroup or security-policy change is performed by the worker.

Source publication, host staging, activation, successful real conversion and
human acceptance are separate evidence checkpoints.
