# Reusable XML-to-APEXlang mapping engine

FOX 0.32.0 adds a project website route alongside the operator CLI below.

FOX's XML-first engine turns supported Forms source patterns into native APEXlang
using versioned, deterministic mapping code. Codex is used during engineering to
understand patterns, implement mappings and verify them. A customer conversion
reuses the installed mappings; it does not need Codex, a prior AI job, or a model
call to reinterpret a supported pattern.

## Architecture

```text
Preserved Forms XML
  -> bounded source parser: objects, code, relationships, hashes, locations
  -> deterministic structural mapping policy and source-bound blueprint
  -> native component plan and complete source disposition ledger
  -> existing native APEXlang renderer
  -> parsed business-rule plan and exact source/target binding
  -> behavior renderer and current package provenance
  -> whole-project SQLcl format validation
```

Binary FMB extraction remains the existing Oracle Forms tooling step. This entry
point starts from XML. It does not parse FMB binary content or invent unavailable
PLL, report or database package bodies.

The structural blueprint is generated by installed mapping code. Its provenance
is deterministic, with no AI-review claim. The existing separately authorized
AI mapping route remains available; this engine does not change retained jobs or
automatically submit unsupported source to a model.

## Current mapping scope

| Source evidence | Generated target | Boundary |
| --- | --- | --- |
| Explicit database block | Native read-only report and synthetic supporting table | No inferred customer table, key, relationship, transaction or CRUD behavior |
| Explicit control block | Native page containing supported control items | No inferred persistence or actions |
| Supported field datatype, length, label and item type | Existing native item/column mapping | Existing fallback and unsupported-property findings remain visible |
| Complete supported numeric field formula | Oracle SQL report projection generated from a closed expression tree | Same-block direct NUMBER inputs only; persisted synthetic rows |
| Complete supported nonzero guard/message/failure/focus trigger | Linked validation-only page and Continue action | Explicit web lifecycle adaptation, independent source minimum, no save/commit |

The expression grammar covers decimal literals, NULL, numeric item references,
parentheses, unary signs, arithmetic `+ - * /`, and CEIL, FLOOR, ABS, ROUND, TRUNC
and NVL with bounded arity. References are bound to exact source items and target
columns. The renderer validates the expression tree and bindings independently;
source text is never inserted as arbitrary SQL. Computed/summary inputs,
cross-block references, unknown calls, strings and extra active statements remain
unsupported. A source division is retained; no divide-by-zero fallback is invented.

The engine emits native Oracle functions rather than approximating calculations
in Python. Oracle documents the semantics of [NVL](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/NVL.html),
[ROUND](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/ROUND-number.html)
and [TRUNC](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/TRUNC-number.html).

The current renderer admits at most 100 behavior operations per package and one
linked validation action per report. The planner admits supported operations in
stable source order. Excess otherwise-supported units remain explicitly
unsupported with a capacity reason; they do not disappear or abort the rest of
the package. These bounds are recorded in the runtime catalog.

## What the mapping library contains

The executable library contains a structural policy, a bounded expression parser,
source/target binding checks, native rendering rules and a versioned mapping
catalog. Each supported mapping has an identity/revision and stated limits. The
output records which mappings were applied and their source/target links. This
is a reusable conversion library, not a trained model or an editable table of
unvalidated source substitutions.

Keep two separate measures:

- Structure: objects planned/rendered, with explicit adaptations and unresolved
  objects. A generated block does not mean its triggers or relationships work.
- Behavior: complete code units generated/wired versus unsupported/missing input.
  One expression and one large approval procedure do not represent equal work.

A form with no supported business pattern can produce an explicitly structural
prototype. A source set with no renderable block must not produce an unrelated
sample application or claim success.

## Reliability and completion

Every run rebuilds facts from original input and binds plans, rules and artifacts
to the source. Existing source/parent packages are not overwritten. Whole-project
format validation uses the installed compatible SQLcl compiler and the generated
project's existing MMD version. Oracle documents [metadata-driven validation and
SQLcl /nolog](https://docs.oracle.com/en/database/oracle/apex/26.1/apxdc/using-sqlcl-apexlang.html).

Generated, format validated, imported, runtime verified and business accepted
remain separate facts. SQLcl format success does not execute supporting SQL,
resolve external objects or verify Forms lifecycle equivalence. The library/operator entry point remains available. Version 0.32.0 also connects
this route to the project website; actual hosted deployment and acceptance must
be checked against that release record.

## Extend knowledge into a reusable rule

1. Inspect representative source and write the exact semantic contract: trigger
   event, data context, conditions, state changes, transactions and dependencies.
2. Define explicit applicability and unsupported variants. Keep source-specific
   names, values and destinations in bindings rather than hardcoding a customer.
3. Implement a bounded parser/binder and renderer; give the rule an ID/revision.
4. Exercise different forms and renamed fields, positive and negative cases,
   injection/ambiguity boundaries and interactions with existing mappings.
5. Validate the generated project and retain all unresolved source. Add target
   execution evidence separately before claiming runtime or business acceptance.
6. Publish the reviewed rule and changelog. Future matching inputs reuse it.

Next priorities are native declarative required/range/default/LOV mappings and
shared parent-child record context. Transactional approvals, record-buffer
semantics and external calls require their own contracts and source evidence.

## Operator usage

Use the existing FOX Python environment with the converter component available.
From the repository root, list the installed mappings:

```bash
python -B products/fox/tools/generate_xml_apex.py --list-mappings
```

Generate one application from the two supplied synthetic example modules:

```bash
python -B products/fox/tools/generate_xml_apex.py \
  --xml products/fox/examples/xml-mapping/invoice.xml \
  --xml products/fox/examples/xml-mapping/stock.xml \
  --project-id mapping-example \
  --project-name "Reusable mapping example" \
  --approved-policy-id fox-demo-synthetic-schema-v1 \
  --output /private/output/mapping-example-1 \
  --validate-sqlcl
```

The explicit policy selects synthetic-prototype behavior; it does not authorize a
database operation or source transfer. Up to four original XML documents are
supported by the existing source contract. Use a new output directory. Duplicate
source names/bytes, unsafe input and unsupported source sets are rejected.

Configure `FOX_EXPORT_SQLCL_PATH` to the existing SQLcl executable if needed.
The CLI writes `candidate.zip`, `generation-report.json` and `result.json`.
Successful requested format validation additionally produces
`APEXlang-xml-package.zip`, `format-validation.json` and retained compiler logs.
Without validation, the candidate remains explicitly pending. A failed command
may leave diagnostic artifacts; the presence of a ZIP alone is not a success flag.

The sample stock trigger deliberately calls an unavailable external routine. It
must remain in the unresolved behavior ledger even though its block and formulas
can be generated. Pack-size division retains source behavior, including a possible
zero-denominator error; no implicit business policy is added.

## Project website workflow (0.32.0)

1. Open the project and select the intended source version. Existing FMB
   preparation can supply XML; the mapping route requires the complete selected
   source set to consist of supported XML files. It never silently drops other files.
2. Under Convert, review Reusable XML mapping and confirm the partial synthetic
   scope and processing on the FOX server. No source is sent to AI by this route.
3. Start the mapping run. The queue retains source/version/catalog/owner consent
   and the request identity. Closing or refreshing the browser does not start a
   second job. If the response is uncertain, check saved status before any retry.
4. Use Convert or APEX output to inspect saved runs and exact reported code counts.
   A generated package has passed fresh SQLcl format validation, not runtime or
   business acceptance. Download is bound to retained original source and evidence.

Active or uncertain mapping requests fence other project mutations in the browser;
read-only status remains available. Source or catalog changes before compilation
stop the job. Interrupted processing becomes attention on restart and requires
reconciliation; it is not replayed automatically. Historical AI runs and their
approvals remain unchanged. This route has no model calls or database imports.

The initial hosted route is disabled for the separately fenced fresh-installation
mode until its dedicated admission contract is implemented. An installed SQLcl
compiler is required; a configured AI provider or target database is not required
for reusable-mapping generation itself.
