# Continue with a reviewed structure correction

This continuation handles a specific stopped prototype run: a parent Forms
module was marked omitted while its child objects were proposed for conversion.
The parent may need to remain as nonvisual structure. That correction is a new
proposal requiring independent review, not permission to invent missing logic.

## What the user sees

1. Open the saved run and select **Check repair plan**. This only reads evidence.
2. Review the prototype scope. FOX locks the original selected code units to
   the same source and target; it does not restart the whole form.
3. Confirm redaction, permission for the configured external AI route, and the
   synthetic-prototype scope again.
4. Select **Continue with corrected structure**. FOX reuses the exact reviewed
   correction and saved clause analysis. It reviews the next saved section with
   its related screen context, then continues unfinished sections only if that
   review passes.

The earlier failed attempt remains in history. A lost response does not trigger
another submission; check the saved run before taking further action.

## What the correction can change

The supported proposal changes one eligible FormModule from an omitted visual
container to unresolved, retained nonvisual metadata. It does not add a page,
process, database key, business rule or executable behavior. Original mappings,
unrelated objects and raw model responses remain unchanged.

FOX checks the approved prefix against the original source before further
generation and checks shared screen references before review. A proposed child
cannot silently survive beneath an omitted parent. Selected trigger bodies and
their mapped actions remain subject to complete source coverage checks.

The existing clause proof and new container proof have separate provenance.
The container proof is reused only for the exact candidate independently
approved. The next section's earlier rejection remains visible to its new
reviewer. No old rejection is relabelled as approval.

## Preserved state and export checks

Continuation appends a fourth source-, owner-, target- and predecessor-bound
record to the same run. Operator-prepared evidence is not user consent; the
authenticated confirmation and durable event are separately required.

Original files and result histories remain hash-bound. The previous latest
result is preserved byte-for-byte before a new terminal result can replace that
pointer. An interrupted publication blocks further processing rather than
replaying a model or database operation.

The output and download endpoints recheck current ownership, selected source,
target, continuation events and retained proof. Download checks run again after
the private package read. Repeated proof reads may share validated values within
one bounded read operation; there is no approval cache across requests, model
calls or package transfers.

## Limits

- This is an operator-prepared continuation for a recognized, fully recorded
  pre-database failure, not a general retry or automatic repair loop.
- Missing or conflicting evidence, changed source, unknown operations and later
  database work are not bypassed.
- The upgrade checker can recognise that a rejected run ended safely. That
  classification grants no retry, proof adoption or conversion-success status.
- Independent review, deterministic validation, unique import and applicable
  runtime checks still gate the output. A reviewed structure is not an APEX file.
- **APEX generated**, **technical checks passed** and **business behavior
  accepted** remain separate facts. Clean-schema reimport and compatibility with
  an unspecified customer target are not established by a prototype export.

Source tests with authored provider and database responses are not live
conversion evidence. Deployment and the actual real-file result must be reported
separately for each installation.
